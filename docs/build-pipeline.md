# Build pipeline — git-managed patches → flashable artifacts

This is the orchestration + patch-management layer **on top of** the per-component
repack mechanics in [rebuilding.md](rebuilding.md). Goal: one reproducible command
turns the pristine vendor firmware plus a set of reviewable, git-tracked patches
into a flashable artifact set, with anti-brick verification gates.

Status: **design** (nothing built yet). The per-component repackers it drives are
specified in rebuilding.md; several still need writing (`mst9u_merge.py` repacker,
`act_repack.py`) and none is hardware-proven.

## Principles

1. **Pristine inputs are immutable and hash-pinned.** We never edit a vendor file
   in place. Every change is a patch.
2. **Patches are declarative text, not binary diffs.** Binary `.patch` files don't
   review and break the moment an offset shifts. Patches describe *intent*
   (symbol, string, hook) and carry a drift guard.
3. **Round-trip before trust.** A repacker must turn an unmodified input into a
   byte-identical output before any patch rides on it (the rebuilding.md golden
   rule), enforced in CI.
4. **Deterministic & reproducible.** Runs in the existing Docker toolchain; same
   inputs + patches → same bytes. Every output carries a provenance manifest.
5. **Never auto-flash.** The pipeline produces artifacts + a report; flashing is a
   separate, deliberate, per-component step with its recovery path established
   first.

## Inputs

- `firmware/original/` — untouched vendor files per component. Large (install.img
  177 MB, part_rootfs 244 MB), so **gitignored** and pinned via `inputs.lock`
  (SHA-256 + provenance per file). The build **fails** if an input hash drifts.
- Derived intermediates (`ap_decompressed.bin`, unpacked rootfs, …) are
  regenerated by the build and gitignored.

## Patch representation

Patches live under `patches/<component>/<feature>/` as a `patch.yaml` manifest
plus any payload files (`.s`, overlay trees). A manifest is an ordered list of
typed ops. Op types:

| type | use | drift guard |
|---|---|---|
| `byte` | literal/flag edit at a symbol or offset | `expect` hex must match |
| `asm` | in-place AEON instruction edit (flip branch, change imm) | `expect_asm` must re-encode to the bytes found |
| `string` | OSD glyph-table text edit (handles the glyph-index cipher + length/offset tables, so length-changing edits like `unplg`→`unplug` work) | `expect` decoded text |
| `inject` | code-cave hook: assemble `asm: file.s`, place in free space (BSS/padding/append), patch a trampoline at `hook:`, preserve displaced insns | `expect` at hook site |
| `fs-overlay` | Linux images: overlay a file tree + run a script (rooting, add a daemon) against the extracted rootfs | n/a (file-level) |

Each patch header: `id`, `component`, `target` (sub-artifact), `description`,
`enabled`, optional `requires` (ordering/deps), and a link to the
feature-targets.md entry it implements.

**Symbol resolution.** Ops may address `symbol[+offset]` from
`tools/aeon-ghidra/symbols.tsv` (RAM addresses). The build resolves symbol → file
offset through the known mapping (`RAM − 0x180000` = combined-image offset;
AP-decompressed offset = combined − 0x3800). The `expect` guard turns any symbol
drift or re-analysis shift into a loud failure instead of a silent mis-patch.

Example (`patches/scaler/a-nosignal-color/patch.yaml`):

```yaml
id: a-nosignal-color
component: scaler
target: ap            # the decompressed AP stream
description: Force no-signal background colour (see feature-targets.md a)
enabled: true
ops:
  # placeholder — exact op (byte vs inject) pending the renderer trace
  - type: asm
    at: osd_no_input_handler+0x?? 
    expect_asm: "..."
    replace_asm: "..."
```

## Per-component pipelines (wrap existing tools)

Each is `unpack → apply patches → repack → verify`, reusing rebuilding.md:

- **Scaler (`MERGE.bin`)** — **WRITTEN.** `tools/mst9u_merge.py` (repack +
  round-trip) and `tools/build_scaler.py` (apply asm cave + size-neutral data
  patches + auto git-hash **version stamp**, with `expect` guards and a container
  self-check). Flow: unpack → inflate AP → apply byte/asm/string ops →
  re-DEFLATE raw (`zlib -15`, lvl 9) → fix CRC-16 + header CRC-32 (incl. the
  solved `0x1b41bbca`) + trailer CRC-32 + `ap_flash_end`/`ap_ram_end`/`filesize`
  + TEL offset fixup. Proven on hardware (see rebuilding.md §1).
- **Network (AM8250, `ACTUPGRADE.bin`)** — `act_unpack.py` → edit ext2 rootfs →
  splice → recompute additive sum (`act_repack.py`, to write). Cleanest target.
- **Actiontec (RTD1295, `install.img`)** — untar → edit `rootfs.ext4.bin` via
  loopback/`debugfs` → re-tar in original order. Needs a working ext4 opener.
- **NXP (`.hex`)** — byte-patch app region only (keep `0x0–0x2000` and the
  `0x1ff00` config record); optional C hook via `arm-none-eabi-gcc` into free
  flash; merge to `.hex`. Flash with `nxp_flash.py`.
- **Nuvoton / DDP** — parked (plausible / not understood; not needed yet).

## Orchestration

- `build/` with a `Makefile` (or `build.py`): `make <component>`, `make all`,
  `make profile-<name>`. Components build independently.
- A top-level `build/profiles/*.yaml` selects which patch sets are enabled per
  build (e.g. `minimal` = feature a only; `full` = all). Lets us ship a tiny,
  low-risk first image.
- Linux-image steps (ext4/tar/mke2fs) and the AEON steps all run in Docker for
  reproducibility.

## Verification & anti-brick gates (CI-enforced)

1. **Round-trip** — each repacker with no patches must reproduce the input
   byte-for-byte. Hard CI gate.
2. **Input hash pinning** — `inputs.lock`.
3. **Patch `expect` guards** — drift detection at apply time.
4. **Diff report** — re-extract the built artifact and confirm *only* intended
   regions changed; any unexpected delta fails the build.
5. **Container self-check** — recompute/verify all CRCs & sums; assert sizes
   within the flash budget.
6. **Provenance** — `dist/manifest.json` (per-artifact SHA-256, input hash,
   applied patch ids, toolchain versions) + human-readable `dist/REPORT.md`
   (changes, diff maps, CRC results).
7. **Recovery precondition** — each component's flash step is gated on its
   recovery path being established first (e.g. scaler: external SPI programmer
   identified and wired **before** the first flash — it is the highest-risk
   component).

## Outputs

- `dist/<component>/…` — artifacts in vendor flash format (`MERGE.bin`,
  `ACTUPGRADE.bin`, `install.img`, `.hex`), plus the stock update-package folder
  layout if the updater expects one.
- `dist/manifest.json` + `dist/REPORT.md`.

## Repo layout (proposed)

```
patches/<component>/<feature>/patch.yaml (+ .s, overlay/)
build/ Makefile  build.py  profiles/*.yaml
build/tools/     byte_patch.py  asm_patch.py  string_codec.py  inject.py  fs_overlay.py  (wrap tools/)
firmware/original/   # gitignored, hash-pinned via inputs.lock
dist/                # gitignored outputs + manifest
inputs.lock
```

## Phasing (confidence-first; mirrors rebuilding.md's order)

1. **Scaffolding + round-trip harness** for the scaler (fully-solved container)
   and AM8250 (easiest). Prove no-op repack is byte-identical. No patches yet.
2. **Patch engine v1**: `byte` + `string` ops, symbol resolver, `expect` guards,
   diff report. Land feature **b** (`unplg`→`unplug`) and feature **a** (colour)
   as first real patches — the colour op shape (`byte` data edit vs `asm`/`inject`
   code patch) is chosen once the no-signal renderer location is confirmed.
3. **`asm`/`inject`** ops (AEON hook) + the NXP app-patch/hook path.
4. **`fs-overlay`** (rooting) for RTD1295 / AM8250.
5. **CI** wiring + manifest/report gates.

## Open dependencies

- Feature **a**'s exact patch (data edit vs code hook, and where) depends on the
  in-progress no-signal-renderer trace — the engine supports both shapes, so the
  pipeline isn't blocked, only that one patch file is.
- Scaler and AM8250 repackers still need writing + a round-trip proof before any
  real build is trustworthy.
